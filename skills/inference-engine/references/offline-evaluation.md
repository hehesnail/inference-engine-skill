# 离线批量评测与吞吐

先确认用户要比较生成、loglikelihood/候选评分，还是整套评测耗时。在线服务的 TTFT/TPOT、离线生成 tok/s、评分题/s 回答不同问题；共同的版本和缓存控制见 [benchmarking.md](benchmarking.md)。

## 固定实际工作量

- 复用指定请求计划或评测脚本，保留原始记录数、执行数、顺序、筛选理由和失败。文本、tokenizer、模板、输入 IDs、截断及 stop 条件会改变有效工作量。
- 生成记录实际完成请求数、输入/输出 token 和长度分布。用实际输出 token 计吞吐，不以最大生成长度乘请求数替代。长度变化可能来自语义变化，需与纯执行加速区分。
- 评分说明一题有多少候选、计分 token 区间、是否复用前缀，以及分数如何聚合；按问题报告题/s、候选/s 或计分位置/s，不把没有生成循环的评分称作 decode TPOT。
- 区分固定 batch、队列持续补充和整批静态分桶。报告请求池大小、每副本 batch、调度上限与 TP/PP/DP；总 GPU 数相同不代表运行方式相同。

## 计时与对照

一次测量明确包含哪些阶段：加载、编译/图捕获、预热、tokenization、排队、模型执行、输出处理与评测统计。关注整轮耗时时保留端到端结果；只计 forward 的结果另行标明。不要拿不同计时边界计算加速比。

整机吞吐使用同一协调时间窗的总工作量除以墙钟耗时，例如 `sum(completed_output_tokens) / (last_finish - common_start)`；该时间轴需来自同一协调器或已校准的时钟。并行 worker 单独计时的吞吐相加只能描述其各自窗口，不自动等于整轮实测吞吐。单卡、单副本与整机指标分栏给出，并交代慢 rank 和尾部未满 batch。

当目标是大队列离线评测时，正式对照覆盖目标队列、batch 和并行方式；单请求延迟可帮助解释，却不能替代吞吐结果。只覆盖本任务要求的工作负载，不由此扩展出全硬件或全模型矩阵。

一个候选可能同时有“相对旧评测基线”和“相对当前 main”两个比值，分别写明分母的源码、权重、配置和计时边界。保存各自原始数值，不能将对旧版本的加速比用于描述对最新实现的收益。

## 优化是否真正生效

将“实现了”“默认开启”“本次进入该分支”“该条件下验证通过”分开报告。检查有效 flag、shape/阶段 guard、fallback、图捕获与实际 dispatch；代码中存在合批不代表所有阶段已经合批。仅部分请求或层进入时注明比例或适用条件，未测到的分支保留未知。精度证据的边界见 [numerical-validation.md](numerical-validation.md)。

使用目标版本已有的评测或 benchmark 入口。包内指南若引用该版本没有的命令，可用项目现有 harness 完成同一测量并说明差异；不为匹配指南升级被测环境。

正式吞吐用未开 profiler 的匹配运行；trace 用于解释热点、调度空洞和通信尾部。先复用已有有效结果，只有版本、输入、配置或待回答问题变化时补相关测量。

交付以用户关注的工作负载为主表：基线与候选的有效条件、实际工作量、计时范围、吞吐/耗时、比值和适用限制。将指标解释与结论放在原始大表之前；不要让用户自行从多份日志拼出单卡与整机结果。

## 输入和评测协议

使用 [Tokenizer与结构输出契约](tokenizer-and-structured-output.md) 对齐模板、special tokens、offsets、grammar、stop与retry。generation/chat endpoint不能自动覆盖loglikelihood任务；固定harness/task/filter版本，保留实际执行与失败数。结构合法与业务正确分别评分，重试计入总tokens、请求数和端到端延迟。
