# 数值基线、验收与候选启用

这份参考用于模型移植、kernel 替换、合批、缓存或状态优化。沿用用户指定的基线和验收脚本；缺失的必要定义先从当前任务与已有记录寻找，不能自行换成更容易通过的实现。

## 对齐对象与协议

记录足以区分本次对象的身份：源码/补丁或镜像、实际 import 位置、权重与 tokenizer revision、精度、输入计划、runner 和有效开关。对照应保留独立且未被候选改写的参考；同一改动后的完整 forward 与增量 forward 一致，只能证明这两条路径内部一致，不能证明与原始 HF、其他框架或旧基线一致。

将验收粒度说清楚：逐位相等、logits 容差、top-1、完整生成序列和评测分数不是相互替代的条件。按指定脚本报告比较位置、样本/步数、阈值及通过数；只检查 top-1 时结论也只到 top-1。必要的诊断指标可以补充，但不自行变成新门槛。

基线与候选使用同一输入、状态初值和协议。涉及有状态执行时，确认预填充、增量步、序列长度和 reset 条件；涉及评分时确认选择的 hidden rows、logit 索引和候选聚合。只验证受修改影响的路径和相关边界，不机械执行所有组合。

若要判断差异是否由本次改动引入，可在相同条件下比较未修改基线、候选以及任务需要的外部参考。若基线也有同一差异，先记录其归属和影响；不能仅据此把候选判为新增回归。用户修改基线或验收口径后，明确新旧证据分别适用于什么结论。

跨实现或执行方式变化后的数值差异，查[数值漂移排查](numerical-drift-debugging.md)，按实际现象选择机制核对和因果验证方法。文中的算子例子是条件案例，不预设根因、修复方式或新增门槛。

## 条件性优化与交付

交付候选时分别说明：实现位置、默认开关、实际启用条件、fallback、已验证范围及尚未验证的分支。检查运行时有效值与 dispatch；“环境变量存在”或“代码已合入”不证明本轮进入优化路径。

例如，某优化仅在普通 decode 的一组 shape 下通过指定对照，则只支持该范围内的启用判断；不能外推到 mixed prefill/decode、chunked prefill 或评分，也不能写成所有输入均已合批。条件示例需要依实际实现选择，不固定某个模型的阈值。

复用源码、参数和输入协议仍然适用的已有证据。先完成约定验收；范围外发现单独说明影响，进一步研究或改变发布/启用范围需与任务目标衔接，不擅自增加精度矩阵、回滚已验收候选或阻塞交付。若发现确由本次修改引入且影响约定范围的回归，仍应修复并补对应验证，不能用其他用例已通过来排除它。

报告结果区分“按指定协议通过”“补充观察”和“未验证条件”，并注明生产发布或默认开启是否属于本次任务。精度通过不自动授权 GPU 实验、改默认值或部署。

涉及 kernel 替换时，输出数值之外还需确认原位状态、alias/stride、量化布局与实际 dispatch；具体例子见 [kernel 接线](kernel-engine-integration.md)。缺失或不完整的测试记录不能当成通过；记录格式与候选保留见 [优化工作流](optimization-workflow.md)。
